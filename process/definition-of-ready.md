# Definition of Ready (DoR)

**Статус документа:** Approved  
**Версия:** 1.0  
**Дата:** 2026-09-05  
**Владелец:** Tech Lead  
**Область применения:** все User Stories и задачи в проекте Food Delivery Platform

## Назначение

Definition of Ready определяет минимальный набор критериев, которым должна соответствовать User Story (или задача), прежде чем она может быть взята в спринт.

Задача, не соответствующая DoR, **не берётся** в спринт.

## Критерии Definition of Ready

User Story считается Ready, если выполнены **все** пункты ниже:

### 1. Бизнес-ценность и ясность
- [ ] Понятна бизнес-ценность (зачем мы это делаем)
- [ ] Сформулирована в формате User Story (As a… I want… So that…) или чётко описана как техническая задача
- [ ] Есть чёткие Acceptance Criteria (минимум 3–5 проверяемых пунктов)

### 2. Детализация
- [ ] Acceptance Criteria написаны на языке, понятном и разработчику, и тестировщику
- [ ] Описаны основные сценарии (happy path) и ключевые альтернативные/негативные сценарии
- [ ] Указаны ограничения и non-functional requirements (если есть): производительность, безопасность, доступность и т.д.

### 3. Зависимости
- [ ] Выявлены все зависимости от других сервисов / команд / внешних систем
- [ ] Зависимости либо уже реализованы, либо запланированы в том же (или предыдущем) спринте
- [ ] Нет блокирующих внешних зависимостей, которые команда не контролирует

### 4. Оценка и объём
- [ ] Story оценена командой (Story Points или идеальные часы)
- [ ] Объём задачи позволяет завершить её в рамках одного спринта
- [ ] При необходимости Story декомпозирована на подзадачи

### 5. Готовность к разработке
- [ ] Есть ссылка на соответствующую страницу в Confluence (детальное описание)
- [ ] При необходимости приложены макеты / API-контракты / схемы
- [ ] Понятно, в каком сервисе (репозитории) будет выполняться работа
- [ ] Нет открытых критичных вопросов к Product Owner / аналитику

### 6. Технические предпосылки (для технических задач)
- [ ] Понятен затронутый сервис и его текущее состояние
- [ ] Учтены требования к обратной совместимости API (если меняется контракт)
- [ ] При изменении схемы данных — понятен подход к миграции (Flyway)

## Как применяется

1. На Sprint Planning команда проверяет каждую кандидату в спринт по этому чек-листу.
2. Если хотя бы один пункт не выполнен — задача возвращается в Backlog на доработку.
3. Product Owner и Tech Lead несут ответственность за то, чтобы задачи доводились до состояния Ready до планирования.
