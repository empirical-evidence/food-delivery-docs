# ADR-004: OpenFeign + Resilience4j для синхронных вызовов

**Статус:** Accepted  
**Дата:** 2026-09-05  
**Автор:** Tech Lead  

## Контекст

Сервисы Food Delivery Platform будут вызывать друг друга синхронно по HTTP (REST).  
Необходимо выбрать способ реализации HTTP-клиентов и обеспечить устойчивость к временным сбоям, таймаутам и деградации зависимостей.

Требования:
- Удобная интеграция со Spring Boot
- Декларативный стиль клиентов
- Поддержка таймаутов, retry, circuit breaker, bulkhead
- Минимальный boilerplate
- Хорошая наблюдаемость (логи, метрики)

## Решение

Для синхронных межсервисных вызовов принимается связка:

- **OpenFeign** — в качестве HTTP-клиента (декларативные интерфейсы)
- **Resilience4j** — в качестве библиотеки устойчивости (Circuit Breaker, Retry, TimeLimiter, Bulkhead, RateLimiter)

Основные правила:
- Каждый исходящий вызов к другому сервису идёт через Feign-клиент
- На Feign-клиенты настраиваются политики Resilience4j
- Таймауты обязательны
- Circuit Breaker обязателен для критичных зависимостей
- Fallback-методы применяются там, где это бизнес-осмысленно

## Альтернативы

### 1. RestTemplate
Устаревший подход. Не рекомендуется в новых проектах на Spring Boot 3.

### 2. WebClient (реактивный)
**Плюсы:** неблокирующий I/O.  
**Минусы:** усложняет код, требует более глубокого понимания реактивного стека. На текущем этапе команда работает в императивном стиле.

### 3. Только Resilience4j + ручные HTTP-вызовы / другой клиент
Отклонено: OpenFeign даёт лучший баланс декларативности и интеграции со Spring Cloud.

## Последствия

### Положительные
- Единообразный и читаемый способ описания клиентов
- Встроенная поддержка устойчивости без большого количества кода
- Хорошая интеграция с Spring Cloud и экосистемой Spring Boot 3
- Легко добавлять метрики и наблюдать за поведением вызовов

### Отрицательные
- Нужно правильно настраивать таймауты и параметры Circuit Breaker (иначе можно получить каскадные отказы или наоборот — слишком агрессивное срабатывание)
- Дополнительная конфигурация в каждом сервисе
- При неправильном использовании fallback можно скрыть реальные проблемы

### Компенсирующие меры
- Единые рекомендации по настройке Resilience4j (будут зафиксированы в шаблоне сервиса)
- Обязательные таймауты
- Мониторинг состояния Circuit Breaker’ов
- Ревью конфигураций устойчивости в Pull Request’ах
