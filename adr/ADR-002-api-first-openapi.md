# ADR-002: API-first подход + OpenAPI

**Статус:** Accepted  
**Дата:** 2026-09-05  
**Автор:** Tech Lead  

## Контекст

В микросервисной архитектуре контракты между сервисами являются критически важным элементом.  
Необходимо определить, как мы проектируем, документируем и развиваем API.

Основные проблемы, которые нужно решить:
- Избежать ситуации «код написан — документация устарела»
- Дать возможность параллельной разработки клиентов и серверов
- Обеспечить единый и машиночитаемый источник истины для контрактов
- Упростить генерацию клиентов, серверных заглушек и документацию

## Решение

Мы принимаем **API-first** подход с использованием **OpenAPI 3.x** в качестве источника истины:

1. Сначала проектируется и ревьюится OpenAPI-спецификация.
2. Только после согласования контракта начинается реализация.
3. OpenAPI-спецификация хранится в репозитории сервиса (обычно в `src/main/resources/openapi` или отдельной папке `api`).
4. Из спецификации при необходимости генерируются серверные интерфейсы и клиенты.
5. Любое изменение контракта сопровождается обновлением OpenAPI-файла в том же Pull Request.

## Альтернативы

### 1. Code-first (сначала код, потом документация)
**Плюсы:** быстрее начать писать код.  
**Минусы:** документация почти всегда отстаёт, сложно проводить ревью контракта до реализации, выше риск breaking changes.

### 2. Использование других форматов (GraphQL schema, gRPC Protobuf как единственный контракт)
Отклонено на текущем этапе: команда и экосистема Spring Boot + REST наиболее зрелы именно вокруг OpenAPI. gRPC может быть рассмотрен позже для внутренних высокопроизводительных взаимодействий.

## Последствия

### Положительные
- Контракт становится предметом ревью до написания кода
- Возможность параллельной работы frontend / других сервисов
- Единый машиночитаемый источник для документации, генерации кода, контрактных тестов
- Легче отслеживать breaking changes

### Отрицательные
- Требуется дисциплина: нельзя «быстро поправить» код без обновления спецификации
- Нужно освоить написание качественных OpenAPI-описаний
- Небольшой overhead на старте каждой новой фичи

### Компенсирующие меры
- Обязательная проверка в DoD: «Если менялся API — обновлена OpenAPI-спецификация»
- Использование инструментов валидации OpenAPI в CI
- Шаблоны и примеры хороших спецификаций в репозитории документации
