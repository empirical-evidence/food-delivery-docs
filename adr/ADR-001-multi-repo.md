# ADR-001: Multi-repo подход

**Статус:** Accepted  
**Дата:** 2026-09-05  
**Автор:** Tech Lead  

## Контекст

Мы разрабатываем Food Delivery Platform как набор независимых микросервисов.  
Необходимо принять решение о стратегии организации исходного кода: монорепозиторий (monorepo) или multi-repo (отдельный репозиторий на каждый сервис).

Ключевые требования:
- Команды должны иметь возможность развивать сервисы относительно независимо
- Чёткие границы владения кодом
- Возможность независимого версионирования, CI/CD и деплоя
- Простота onboarding новых разработчиков
- Масштабируемость на несколько команд в будущем

## Решение

Мы принимаем **multi-repo** подход:

- Один сервис = один Git-репозиторий
- Отдельный репозиторий для документации (`food-delivery-docs`)
- Отдельный репозиторий для инфраструктуры (`food-delivery-infrastructure`)

## Альтернативы

### 1. Monorepo (один репозиторий на всё)
**Плюсы:**
- Проще делать атомарные изменения сразу в нескольких сервисах
- Единый CI и единообразие инструментов
- Легче видеть всю картину

**Минусы:**
- Сложности с правами доступа и владением
- CI становится тяжёлым при росте
- Выше риск «случайных» зависимостей между сервисами
- Сложнее независимо версионировать и деплоить сервисы

### 2. Hybrid (несколько логических групп сервисов в разных репозиториях)
Отклонено как усложнение без явной выгоды на текущем этапе.

## Последствия

### Положительные
- Чёткие границы сервисов и командное владение
- Независимые пайплайны CI/CD
- Возможность применять разные версии библиотек и подходы к релизу
- Проще ограничивать доступ к коду при необходимости

### Отрицательные
- Сложнее делать изменения, затрагивающие несколько сервисов одновременно
- Нужно поддерживать единые стандарты (шаблоны репозиториев, code style, ADR)
- Требуется более дисциплинированный подход к версионированию API и событий

### Компенсирующие меры
- Единый шаблон сервисного репозитория
- Обязательные ADR на кросс-сервисные решения
- API-first + строгие контракты (OpenAPI)
- Чёткий Git-flow и защита веток
