# ADR-005: PostgreSQL + Flyway

**Статус:** Accepted  
**Дата:** 2026-09-05  
**Автор:** Tech Lead  

## Контекст

Каждый микросервис владеет своими данными (Database per Service).  
Необходимо выбрать реляционную СУБД и способ управления схемой базы данных.

Требования:
- Надёжная транзакционная СУБД
- Хорошая поддержка в Spring Boot и Java-экосистеме
- Предсказуемые и версионируемые миграции схемы
- Возможность работать как в локальной разработке, так и в тестовых/продовых окружениях
- Отсутствие «ручных» изменений схемы на окружениях

## Решение

В качестве основной реляционной СУБД принимается **PostgreSQL**.  
Управление схемой базы данных осуществляется с помощью **Flyway**.

Основные правила:
- Каждый сервис имеет свою базу данных (или свою схему — по договорённости)
- Все изменения схемы выполняются только через миграции Flyway
- Миграции хранятся в репозитории сервиса (`src/main/resources/db/migration`)
- Миграции версионируются и применяются автоматически при старте приложения (или через отдельный шаг CI/CD)
- Ручные изменения схемы на окружениях запрещены

## Альтернативы

### 1. MySQL / MariaDB
Возможная альтернатива, но PostgreSQL обладает более мощными возможностями (JSONB, CTE, оконные функции, надёжность) и лучше подходит для сложных доменных моделей.

### 2. Liquibase
**Плюсы:** более гибкий формат изменений (XML/YAML/JSON).  
**Минусы:** выше сложность, тяжелее читать историю изменений по сравнению с простыми SQL-миграциями Flyway.  
На текущем этапе выбран более простой и прозрачный подход — Flyway + SQL.

### 3. Hibernate ddl-auto / автоматическая генерация схемы
Категорически отклонено для всех окружений кроме локальных экспериментов. Небезопасно и неконтролируемо.

## Последствия

### Положительные
- Предсказуемая эволюция схемы
- История изменений схемы хранится в Git
- Легко поднимать базу с нуля (достаточно прогнать миграции)
- Хорошая интеграция со Spring Boot
- PostgreSQL — зрелое и мощное решение

### Отрицательные
- Нужно писать миграции аккуратно (особенно `ALTER` на больших таблицах)
- Требуется дисциплина: нельзя «быстро поправить» схему руками
- При ошибке в миграции на проде восстановление может быть нетривиальным

### Компенсирующие меры
- Миграции проходят code review
- Обязательная проверка миграций в CI
- Использование `flyway clean` только в локальной разработке и никогда на shared-окружениях
- Документирование сложных миграций в описании Pull Request
