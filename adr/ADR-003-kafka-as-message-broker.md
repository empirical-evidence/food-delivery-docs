# ADR-003: Apache Kafka как основной брокер сообщений

**Статус:** Accepted  
**Дата:** 2026-09-05  
**Автор:** Tech Lead  

## Контекст

В микросервисной архитектуре Food Delivery Platform сервисы должны обмениваться данными не только синхронно (через REST), но и асинхронно.  

Типичные сценарии:
- События жизненного цикла заказа (создан, оплачен, готовится, передан в доставку, доставлен)
- Уведомления
- Обновление статусов в реальном времени
- Развязка сервисов и повышение устойчивости к временной недоступности

Необходимо выбрать основной брокер сообщений.

## Решение

В качестве основного брокера сообщений принимается **Apache Kafka**.

Основные принципы использования:
- События публикуются в топики Kafka
- Сервисы являются продюсерами и/или консьюмерами
- Используем паттерн Domain Events / Event-Driven Architecture там, где это уместно
- Гарантии доставки и семантика (at-least-once / exactly-once) выбираются осознанно для каждого сценария
- Схемы событий версионируются и документируются

## Альтернативы

### 1. RabbitMQ
**Плюсы:** проще в освоении, удобные паттерны routing, хороший для task queues.  
**Минусы:** хуже подходит для высоконагруженных event-stream сценариев, слабее модель replay и долгосрочного хранения событий.

### 2. Только синхронное взаимодействие (REST)
Отклонено: создаёт сильную связанность и снижает устойчивость системы.

### 3. Другие брокеры (NATS, Pulsar, AWS SNS/SQS и т.д.)
Отклонены на текущем этапе из-за меньшей распространённости в Java/Spring-экосистеме команды и дополнительных operational-затрат.

## Последствия

### Положительные
- Хорошая горизонтальная масштабируемость
- Возможность хранить историю событий и делать replay
- Слабая связанность сервисов
- Зрелая интеграция со Spring (Spring Kafka)
- Подходит как для event-driven, так и для stream-processing сценариев в будущем

### Отрицательные
- Выше operational complexity (нужно следить за кластером, топиками, consumer groups, retention)
- Сложнее гарантировать exactly-once
- Нужно тщательно проектировать схему событий и их эволюцию
- Локальная разработка требует поднятия Kafka (через docker-compose)

### Компенсирующие меры
- Kafka поднимается в `food-delivery-infrastructure` через docker-compose для локальной разработки
- Обязательное документирование событий (схемы + версионирование)
- Использование Spring Kafka + понятных конфигураций
- В будущем — Schema Registry (при росте количества событий)
